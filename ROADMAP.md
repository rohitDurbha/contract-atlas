# Contract Atlas roadmap

Work moves top to bottom, one step at a time. A step is ticked when it ships and an item is ticked when all of its steps are done.

Already shipped on Nov 3 and 4, 2026. Fifteen dead sources were retired (43 remain), the feed shows a 90-day contract-only window, reposted openings are collapsed, snapshot pruning brought the database from 30 MB to about 17 MB, a Cloudflare cron dispatcher keeps the two-hour refresh reliable, Vercel deploys on every code push, and the README was rewritten.

## Items

The MCP endpoint is live at `https://contract-atlas-amber.vercel.app/api/mcp` (stateless Streamable HTTP, no login).

- [x] 1. MCP server with more tools, so AI assistants such as Claude can use the feed.
  - [x] a. Add a read-only remote MCP server at `/api/mcp` on the existing Vercel function using the official TypeScript MCP SDK and Streamable HTTP. Tools `search_jobs`, `get_job` and `list_sources` read the bundled SQLite snapshot through the same feed policy the site uses. Add tests.
  - [x] b. Add a `market_trends` tool that computes posting volume, top skills, categories and pay ranges over time from the snapshot in SQL.
  - [x] c. Add an `estimate_pay` tool. Train a simple regression on roles that list hourly pay (title words, skills, category, location, company) during the refresh workflow, save the coefficients as JSON next to the snapshot, and return a range clearly labeled as an estimate.
  - [x] d. Add a `match_resume` tool that takes resume text, ranks current roles by similarity (TF-IDF or small embeddings), explains the overlap and missing skills, and never stores the resume.
  - [x] e. Document the server in the README with connection steps for Claude and other clients, add a `server.json`, and prepare publishing to the official MCP Registry.
- [x] 2. Delete the unused Randstad and LiveHire adapter code and their tests.
  - [x] a. Remove the Randstad feed (`randstadFeed`, `parseRandstad` and the provider branch in the collector) together with its tests, since every Randstad board is retired.
  - [x] b. Drop `Randstad` and `LiveHire` from the provider type, remove the retired Randstad and LiveHire entries from `server/seed.json`, and point the test fixtures that still use those provider names at a live provider.
- [x] 3. Remove the legacy Cloudflare D1 path (root `wrangler.jsonc`, migrations, `build-worker`, `refresh-live`, `verify-live`, the scheduled export and the POST refresh routes) while keeping the Vercel and GitHub Actions path working.
  - [x] a. Delete the Cloudflare deployment files, which are the root `wrangler.jsonc`, `migrations/`, `scripts/build-worker.mjs`, `scripts/refresh-live.mjs`, `scripts/verify-live.mjs` and the `db:local` and `preview` npm scripts. Keep `wrangler` as a dev dependency because the dispatcher deploy still uses it.
  - [x] b. Remove the scheduled export, the POST refresh, refresh step and schedule settings routes and the static asset fallback from `server/index.ts`, drop `startRun` and `stepRun` if nothing else needs them, and update the API tests. `startRun` and `stepRun` stay because `runScheduled` in the refresh script drives collection through them. The site's refresh button now only reloads the published feed.
  - [x] c. Replace the `D1Database` type with a small database interface over `node:sqlite`, so `@cloudflare/workers-types` and the Drizzle D1 driver are no longer needed. The interface lives in `server/database.ts`, and feed queries now run through the Drizzle `sqlite-proxy` driver on top of it.
- [x] 4. Precompute the duplicate flag at collection time and add an index so feed requests do not run a window query on every call.
  - [x] a. Add a `duplicate` column to `jobs` (with a migration for snapshots that predate it) and a `markDuplicates` function that sets the flag in one statement for every reposted opening the feed currently hides. Add tests that compare it with the live window query.
  - [x] b. Run `markDuplicates` at the end of every refresh and when the snapshot is built, then switch `feedScopeSql` to read the flag instead of the window query. Flags are also recomputed after pruning and after the seed loads, and `windowScopeSql` keeps the old query for checks. On the Nov 17 snapshot both list the same 845 roles with 81 reposts flagged.
  - [x] c. Add an index that covers the flag and the freshness columns, and make `verify:free` fail when the stored flags disagree with a fresh window query. The new `jobs_feed` index on `(active, duplicate, posted_at, first_seen_at)` replaces `jobs_freshness`, and `verify:free` also stops when that index is missing. On the Nov 18 snapshot the index did not change request times much (the first jobs page still takes about 300 ms locally) because almost every active role is inside the 90-day window and most of the cost is the technical-title match that runs on each row. Storing that title match as a column at collection time, like the repost flag, would be the next real speedup if feed latency ever matters.
- [x] 5. Mark sources with zero open roles clearly in the source directory and stop counting them as loaded.
  - [x] a. Flag readable sources that currently have no roles in the feed with an `empty` field on each source, and stop counting them as readable, complete or partial in the overview. Report them separately as `emptySources` so the API, the site and the MCP `list_sources` tool agree. Add tests.
  - [x] b. Show a clear "No open roles" badge and a summary tile for those sources in the source directory, and update the home page metric and coverage notice wording to use the new counts. The coverage notice now lists partial, empty and unreadable sources separately and stays hidden when the only shortfall is sources with no open roles.
  - [x] c. Add a directory filter that hides or shows sources with no open roles, and note the behaviour in the README. A button next to the provider filter hides or shows them and states how many there are (19 of 43 on the Nov 18 snapshot). It only appears when at least one source has no roles, every source is shown by default, and clearing the source filters shows them again.
- [ ] 6. LLM enrichment at collection time with a free Groq or Gemini key stored as a GitHub secret. Extract skills, seniority, normalized title, remote status and hourly pay into the snapshot so the site has no runtime AI cost.
  - [x] a. Add a `job_enrichment` table (with a migration for older snapshots) and a `server/enrichment.ts` module that builds the prompt, calls Groq by default or Gemini as the fallback with JSON output, validates the answer with zod and stores it keyed by a hash of the role text. Model names live in one config and can be overridden from the environment. Nothing is called without a key. Add tests with a mocked `fetch`. The defaults are `openai/gpt-oss-20b` on Groq and `gemini-3.1-flash-lite` on Gemini, overridable with `ENRICH_GROQ_MODEL` and `ENRICH_GEMINI_MODEL`, and the keys are listed in `.env.example`. Answers are cleaned before they are stored, so unknown labels become `unknown` and pay outside 5 to 1000 per hour is dropped.
  - [x] b. Run enrichment in the refresh workflow for active roles that are new or whose text changed, with a per-run cap and a small delay between calls so the free tier limits hold, and pass the secret through `refresh.yml`. A missing key or a failing provider must never fail the refresh. `enrichPending` runs after pruning and repost flags, newest postings first, with at most 40 calls a run and four seconds between them (`ENRICH_MAX_PER_RUN` and `ENRICH_DELAY_MS` repository variables override both), and it stops after three failures in a row. Answers are pruned with their role. On the Nov 19 snapshot 847 feed roles are waiting, so once a key is added the backlog takes about two days of refreshes to clear and later runs only see new or edited roles.
  - [ ] c. Read the stored enrichment in the feed, the API and the MCP tools, preferring it over the regex skills and work mode when present, and show seniority and the normalized title on the site.
  - [ ] d. Make `verify:free` check that stored enrichment is well formed, and describe the enrichment, its limits and the secret in the README.
- [ ] 7. Semantic search using small local embeddings (bge-small or MiniLM through fastembed) stored in SQLite with sqlite-vec, so people can describe the role they want in plain words.
  - [x] a. Add a `job_embeddings` table (with a migration for older snapshots) and a `server/embeddings.ts` module that builds the text each role is embedded from, hashes it so unchanged roles are skipped, stores vectors as little-endian float32 blobs (the format sqlite-vec reads) and ranks feed roles by cosine similarity to a query vector. The model sits behind a small embedder interface, so tests use a fake one and need no download. Ranking is a plain scan in JavaScript for now, which is quick for under a thousand roles, and pruning removes vectors together with their role. The deployed snapshot gains the table on its next refresh, so the search in step c has to treat a missing table as no vectors.
  - [ ] b. Embed new or changed active roles in the refresh workflow with `bge-small-en-v1.5` through fastembed, cache the model between Actions runs, and keep the refresh green when the model cannot load.
  - [ ] c. Embed the visitor's query at request time on the Vercel function with the same model, add a `semantic` option to the jobs API and a `semantic_search` MCP tool, and fall back to keyword search when vectors or the model are missing. Load sqlite-vec for the distance query if the brute-force scan becomes slow.
  - [ ] d. Add a "Describe the role" search mode on the site, make `verify:free` check that stored vectors match the model's size, and document the feature in the README.
- [ ] 8. Resume match that runs fully in the browser with transformers.js. The visitor drops a resume, it never leaves the device, and roles are ranked by similarity.
- [ ] 9. A trends page with Plotly or Recharts charts for skill demand, pay ranges and posting volume over time, plus a weekly LLM-written market summary.
- [ ] 10. Tests for the dispatcher worker, a CI workflow for pull requests, and README screenshots.
